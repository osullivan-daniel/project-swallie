Plan: Split the Swallie app into admin and portal

TL;DR: keep the current Angular workspace as the migration backbone, make the two Nx apps the source of truth for the two user-facing surfaces, and move shared contracts into the existing libs/* structure before wiring the backend API. The recovery goal is to reproduce the split cleanly if the workstation dies again, without re-deriving the architecture from scratch.

Current repo baseline
- The workspace already contains the split target apps in apps/frontend-admin/project.json and apps/frontend-portal/project.json.
- The backend placeholder exists in apps/backend/project.json, which should become the API boundary for the two frontends.
- Existing shared model/API scaffolding is already being prepared under the Nx libraries structure in libs/angular/api and libs/angular/models.

Implementation phases
1. Freeze the legacy route map and identify the admin-only vs customer-only screens.
   - Audit the old root app in the current source tree and classify each screen, service, and state model as either admin, portal, or shared.
   - Use the placeholder shells in apps/frontend-admin/src/app and apps/frontend-portal/src/app as the canonical landing points.
   - Depends on: no code change, only classification and a written boundary list.

2. Move the admin surface into the admin app and keep it isolated from the portal.
   - Port the admin dashboard, admin state management, admin routes, and admin-only UI components from the legacy tree into the frontend-admin app.
   - Remove or neutralize admin-only imports from the root workspace build once the new app has its own runtime entrypoint.
   - Keep any shared domain models, API contracts, or utility services in the libs/* layer, not in the app shell.

3. Move the customer surface into the portal app and keep it isolated from the admin.
   - Port the ordering experience and portal-only state management into frontend-portal.
   - Make the portal app responsible for the public customer flow and the admin app responsible for back-office flow.
   - Keep route names and component selectors stable during migration to reduce regressions.

4. Make the backend the single integration point between the two apps.
   - Introduce the API contracts first in the shared libs (order-api.service.ts, catalog-api.service.ts, and model definitions).
   - Point the app shells to the backend through the library services instead of through direct legacy service coupling.
   - Treat the backend as the only place where order/product/admin data is fetched or mutated.

5. Clean up the monorepo boundary and restore build verification.
   - Remove or archive unused legacy root-level app wiring once the admin and portal apps are independently buildable.
   - Re-enable strict typing once the data contracts are stable, then tighten scopes in the shared libs.
   - Final verification uses Nx commands and targeted build/serve checks.

Relevant files to reuse or modify
- package.json — Nx scripts and top-level dev commands for serving/building each app.
- apps/frontend-admin/project.json and apps/frontend-portal/project.json — app build targets that should stay clean and independent.
- apps/backend/project.json — placeholder backend target that must become the real API service boundary.
- libs/angular/api/src/order-api.service.ts and libs/angular/api/src/catalog-api.service.ts — shared backend contract entrypoints.
- libs/angular/models/src/order.model.ts and libs/angular/models/src/product.model.ts — shared data contracts that should be moved out of app-local code.
- src/app — legacy source tree to audit and progressively split down into the two new apps.

Verification checklist
1. Verify the two frontend applications can be built independently:
   - npx nx run frontend-admin:build
   - npx nx run frontend-portal:build
2. Verify the backend placeholder target still exists and can host the new API entrypoint:
   - npx nx run backend:build
3. Verify the runtime boundary by serving each app on its own target:
   - npm run serve:admin
   - npm run serve:portal
4. Confirm route isolation with a simple manual check:
   - admin-only routes should only resolve in the admin shell
   - portal ordering routes should only resolve in the portal shell

Decisions and scope boundaries
- Keep the split as a staged migration, not a one-shot rewrite.
- Do not move every service immediately; move only the code that belongs to the admin or portal boundary, and leave shared contracts in libraries.
- The immediate deliverable is two independently buildable frontends with one shared backend-facing API layer.
- Type safety is intentionally deferred until the API contracts are stable enough to make the library model layer trustworthy.

Recovery note
If the machine crashes again, the safest fallback is to recover from this documented step sequence: classify routes and services, move code into the two Nx apps, then attach the backend boundary through the shared API and model libs. That order preserves the repo shape and makes the split reproducible.
